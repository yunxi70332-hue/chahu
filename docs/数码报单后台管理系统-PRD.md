## 一、先想清楚:我们到底在做什么

### 1.1 业务事实(来自报价表,不是猜的)

- 生意本质:**二手数码回收**。每天一张报价表,店员/代理按表收货、报单结算。
- 产品结构:**手机 996 / 平板 253 / 穿戴 129 / 笔记本 94 / 配件 63**,另有酒水、奶粉、游戏设备、摄影摄像等杂类(共 11 大类)。
- 品牌高度集中:华为、红米、苹果、vivo、小米、OPPO、iQOO、荣耀、一加占绝对大头。
- 单条报价 = 大类 + 品牌 + 型号 + 规格(内存/硬盘/颜色/成色)+ **参考回收价**。
- 报价每天变(全表统一报价日 2026-09-14),部分数据"待核对",个别价格为负(异常)。

### 1.2 结论:系统的核心一句话

> **让报单的人 30 秒内按最新价格提交一笔回收单,让管理者一眼看清今天收了什么、花了多少钱。**

之前 PRD 里"话费/流量/点卡"类假设全部作废;系统围绕**产品库(报价表)+ 报单 + 审核 + 流水**四件事重建。

### 1.3 PM 思考框架(每个功能都过这三问)

| 三问 | 判断标准 |
| --- | --- |
| 谁在用?多久一次? | 每天多次的功能做到最短路径;每周一次的做到不出错即可 |
| 不做会怎样? | 不做生意就停转的 → P0;只是"有更好" → 砍或推迟 |
| 用户要动脑/动手吗? | 能自动带出的绝不手填,能算的绝不让人算 |

## 二、用户是谁:他们的一天

### 角色 A:报单员(店员/代理,高频用户,一天几十单)

- 柜台收到一台机器 → 打开系统 → **搜型号**(如"苹果17"或"华为mate60")→ 列表按品牌/内存/颜色筛 → 找到对应报价 → **确认数量 → 提交**。
- 痛点:报价表 1685 行 Excel 根本翻不动;价格每天变,记不住;填错规格对不上款。
- 他要的:**搜得快、价格自动带出、填的字段少**。

### 角色 B:管理员(老板/运营,一天一次集中处理)

- 早上:导入/核对当日报价 → 看板看昨天经营。
- 白天碎片时间:手机上**批量审单**(通过/驳回),驳回要写一句原因。
- 他要的:**待办明确、批量操作、数字可信**。

### 角色 C:老板(看数,低频)

- 只看看板:今日单量、金额、待审数、哪个品类收得多。
- 他要的:**打开就是答案,不用点第二次**。

> 后台不做会员自助注册;报单人账号由管理员创建(与参考站一致)。

## 三、顺手与简洁:六条设计铁律

1. **搜索是第一入口。** 1685 个 SKU 不做分类树漫游,报单页首屏就是搜索框,输品牌/型号即出结果,规格(内存/颜色)做二次点选,不打字。
2. **能带出不手填。** 选了产品,品类、单价、规格快照全部自动带出;总金额=数量×单价自动算;报单人只填"数量"这一个数字(以及可选备注)。
3. **三步完成报单。** 搜型号 → 点规格确认价格 → 提交。任何一步超过 5 秒都是设计失败。
4. **状态只用三色。** 黄=待审核、绿=已通过、红=已驳回。全站统一,老板扫一眼列表就知道卡在哪。
5. **手机必须能用。** 店员在柜台用手机报单、老板用手机审单;表格在手机上只留:单号/产品/金额/状态。
6. **异常价格不给选。** 回收价 ≤0 或缺失的产品在报单选品里默认隐藏(数据里确实存在 -1400 这类待核对行),避免提交出负数订单。

## 五、核心流程(报单全链路)

```
管理员导入当日报价 ──► 产品库(1685 SKU)
                            │
报单员:搜"苹果17" ─► 选规格/颜色(价格自动带出)─► 填数量 ─► 提交
                            │
                    待审核(黄)
              ┌─────────────┴─────────────┐
          通过(绿)                    驳回(红,必填原因)
              │                             │
   扣报单人货款 + 发佣金                结束,可改后重提
              │
        写入资金流水(余额快照)
              │
        看板数字实时更新
```

规则:审单通过时**余额不足则拦截**(提示差额),先充值再审;驳回的单不改余额。

## 十、5 个决策问题的拍板结果(2026-09-15 已确认,已全部落地)

1. **资金模式** → 回收模式,平台打款:审核通过 = 报单人余额增加 本金+佣金(两笔流水);提现为线下转账后管理员记账扣余额
2. **佣金** → 品类比例自动算(管理员在「产品管理→佣金比例设置」批量配置)+ 报单时可单笔手动改
3. **报价表** → V1 已做 Excel 一键导入(整批替换,价格≤0/空自动下架,返回 导入数/下架数/报价日)
4. **会员端** → 会员登录同一套系统,仅见 报单管理+资金流水,数据仅自己;登录后默认落地 /orders
5. **异常报价** → 默认隐藏:导入即下架,建单选品(available=1)搜不到,产品页可「核对」后重新上架

## 十四、v2.4 中介模式 + 报价自动采集(2026-09-17 交付)

**商业模式转变**:原"平台按大富报价全款打款 + 另发佣金"(贴钱)→ **中介模式**:大富报价为上游价,代理所见/所结为「上游价 ×(1 − 品类下浮%)」的收购价;审核通过按收购价打款一笔流水,**差价 = 系统利润**。佣金机制废弃(commission 恒 0,历史数据只读保留)。

**数据模型**:`Product.upstreamPrice`(上游价,商业机密)、`price` 语义改为代理收购价;`Order.upstreamPrice/profit` 建单快照(利润 =(上游−结算)×数量,议价高于上游为负不拦截、审核列表标红由总部把关);`Setting.markdown_rates` 品类下浮比例。

**报价更新双通道**(同一导入核心,规则/统计口径完全一致):
- **通道 A·脚本自动**:kdocs-export 清洗完成 → 读取 `baodan.json` → 自动 POST `/api/products/import`(`X-Import-Key` 鉴权)→ 产品库即日更。日常"双击 bat + 网页点导出"零手工
- **通道 B·人工上传**:产品管理 → 导入报价表(管理员 JWT 鉴权),作为兜底与回滚手段
- 导入规则:「参考回收价」= 上游价,代理价按品类下浮自动算;上游价 ≤0/空/下浮后 ≤0 → 自动下架(成色备注保留原始价文本);返回统计含本次下浮比例摘要

**权限**:上游价/差价利润仅总部可见——产品列表、订单列表/详情、看板接口按角色裁剪,代理/会员响应中物理不下发。

**看板**:总部新增「今日差价利润」卡(今日已审单 profit 合计);今日打款口径改为收购价货款。

**验收记录(全部实测)**:真实报价表 1685 行经双通道各导入一次结果一致(269 异常下架);五品类下浮抽查 98/97/96/97/95% 精确;改比例→recalc→恢复 全链路 1416 条重算;会员建单响应无上游/利润字段,管理员视角利润快照 =(5840−5723.2)×2 精确;审核通过余额+=货款、单笔 ORDER 流水无佣金;议价单利润 −100 允许提交;看板 todayProfit 仅管理员下发。截图 `qa-screenshots/50~54-*`。管道端到端:receiver 推送函数实测导入成功(脚本通道与网页触发同一代码路径);清洗规则报价日期改为默认当天。

## 十五、v2.5 品类计价双模式(2026-09-17 交付)

**背景**:v2.4 只有「下浮比例」一种计价方式;实际业务中部分品类(如高价机型)更适合按固定金额下浮,故新增第二种计价方式。

**两种计价方式(每行二选一,弹窗提供全局一键切换)**:
- 下浮比例:`代理收购价 = 上游报价 ×(1 − 下浮%/100)`
- 减固定金额:`代理收购价 = 上游报价 − 固定金额(元)`

**数据模型**:`Setting` 新增 key `markdown_rules`,值为 `{ 品类: { mode: 'percent'|'fixed', value } }`。旧 key `markdown_rates` **保留不删**:读取时若 `markdown_rules` 不存在,自动把旧数据规范化为 percent 规则返回,**存量数据无需迁移**;写入只写新 key,避免同一品类两份规则产生优先级歧义。

**接口**:`GET /settings/markdown` 返回 `{ rules, rates }`(`rates` 为 percent 品类派生映射,兼容旧调用);`PUT /settings/markdown` 接收 `{ rules }`,并**兼容旧的 `{ rates: {品类:数字} }` 请求体**(自动按 percent 规范化),部署窗口期旧页面提交不会 400。校验:percent 限 0–100,fixed 限 0–1000000 且不可为负。`POST /products/import`、`POST /products/recalc` 响应新增 `markdownRules`,`markdownRates` 保留。

**计算入口收敛**:计价公式统一收敛到 `backend/src/util.js` 的 `computeAgentPrice(upstream, rule)` 单一函数,导入与重算两条路径共用,避免两处公式漂移;重算时计价 ≤0 的产品置空价格并下架(与导入口径一致,不落库负价)。

**前端**:弹窗更名「品类计价设置」,表格为 品类名称 / 计价方式(下拉)/ 计价数值(单位随方式在 % 与 元 间切换)/ 操作;顶部「全局计价方式」一键套用全部行,单行仍可各自覆盖;导入结果摘要按方式渲染(`手机 −¥100` / `平板电脑 3%`)。

**验收记录(全部实测)**:旧 `markdown_rates` 数据经接口回读正确规范化为 percent 规则(存量无需迁移);混合规则(手机=减 100 元、平板电脑=下浮 3%、配件未配置)下 recalc 1416 条,抽样核对(5840→5740、3280→3181.6、未配置品类 385→385)全部精确;固定减额超上游价时全量自动下架(976 条);小样本 xlsx 经 JWT 与 X-Import-Key 两条通道各导入一次结果完全一致;percent 120 / fixed −5 均被 400 拦截;UI 全局切换与单行切换、单位联动、保存并重算提示「已重算 1416 条」均实测通过,页面无 JS 报错。截图 `qa-screenshots/v25-1~5-*`。
